“

미검출 ≠ 법적 적합

식별할 수 있는 규칙에서 일치하는 항목을 찾지 못한 것과 제품이 법적으로 적합하다는 것은 다른 말입니다. 그래서 화면의 통과(Pass)를 "등록 목록에 일치하는 적용 항목이 없다"는 뜻으로 명시하고, 조건이나 용도를 확정할 수 없는 성분은 확인 필요(REVIEW)로 돌려주도록 했습니다. AI가 규제를 추측하지 않고, 원문 조건과 출처를 함께 보여 줍니다.

여러 농도와 제품 조건의 연결이 불명확숫자를 임의로 연결하지 않고 원문에 보존, 한도 칸은 비우고 확인 대상으로 표시 (예: A2-57의 3.5%와 2.1%)

로딩 단계

1. 원본 행은 지우지 않고 보존
2. 식별 정보가 있는 규칙 → 스크리닝에 사용하는 규칙 목록
3. 식별자가 없는 행      → unidentified 목록으로 따로 분류
4. 그 행을 만나도 국가 데이터 전체는 ready 상태로 로딩
5. 스크리닝은 성분명이나 CAS가 있는 규칙만 사용자 성분과 비교

05 · Reflection

느낀 점

01

API만으로는 부족했다,
그래서 원문을 직접 구조화했다

처음에는 API만으로 성분 분석 기능을 만들려고 했지만, 원하는 수준의 상세 정보(배합 한도, 제품별 조건)가 없다는 한계를 확인했습니다. 그래서 공식 규제 원문을 직접 데이터로 옮기는 쪽을 택했고, 특히 러시아 데이터에서는 식별할 수 없는 행을 지우지 않고 따로 분류하며 원문 조건을 보존하는 방식으로 신뢰도를 지키려 했습니다.

02

AI는 질문 방식에 따라
다르게 썼다

전체 구조나 방향을 잡을 때는 목적과 방향을 먼저 제시하는 Top-down 방식으로, 특정 데이터 처리나 기능 구현처럼 세부 작업에서는 "어디서부터 시작하면 되는지"를 묻는 Bottom-up 방식으로 AI와 협업했습니다.

03

협업의 기본기를
처음 제대로 경험했다

1인 1브랜치, PR 리뷰 후 main 병합, API 키를 .env로 분리하는 규칙을 실제 프로젝트에서 지키며 버전 관리와 보안의 기본을 익혔습니다.

아쉬운 점과 다음 목표

  • 데이터 자동 갱신지금의 데이터는 정적이라 규제나 통계가 바뀌어도 자동으로 반영되지 않습니다. 관리자 기능이나 수집 · API 연동으로 데이터를 갱신하는 구조를 만들고 싶습니다.
